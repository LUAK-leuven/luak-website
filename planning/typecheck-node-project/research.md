# `nuxt typecheck` fails for shared/types, server/domain, app/model

## Problem Statement

`nuxt typecheck` runs 4 separate TypeScript projects generated by Nuxt: `tsconfig.app.json`, `tsconfig.server.json`, `tsconfig.shared.json`, `tsconfig.node.json`. Checked in isolation, `app`, `server` and `shared` are clean (aside from 2 unrelated bugs). Every "cannot find name" / "cannot find module" error comes from **`tsconfig.node.json`**, which is the project Nuxt assigns to build-time config (`nuxt.config.ts`, `vitest.config.ts`, `playwright.config.ts`) and, in this repo, all of `test/**` except `test/nuxt/**`.

Files under `test/unit`, `test/integration`, `test/e2e` and `test/testUtils` import production source (`app/model/**`, `server/domain/**`, `shared/types/**`) using the alias `~/<root-relative-path>` (e.g. `~/server/domain/inventory/InventoryItem`, `~/shared/types/rental`). Once TypeScript pulls a source file into the node program as a dependency, that file is type-checked under the **node project's** `compilerOptions`, not the ones from whichever project it "belongs" to. Two things then break:

| what breaks | why |
|---|---|
| `Cannot find name 'RentalId'`, `'EntityId'`, `'Enums'`, `'UserId'`, `'TopoId'`, ... | `.nuxt/nuxt.node.d.ts` never references `types/shared-imports.d.ts` / `imports.d.ts`, which contain the `declare global { export type {...} }` block that the app/server/shared projects get. Code that relies on Nuxt's type auto-imports (writing `RentalId` with no import) simply has no global declaring it in the node program. |
| `Cannot find module '#server/domain/inventory/ItemEvent'`, `'~~/server/domain/inventory/ItemEvent'` | `nodeTsConfig.paths` in `nuxt.config.ts` only defines `~/*` (remapped to repo root, not `app/`) and `#test/*`. There's no `#server/*`, `#shared/*`, or `~~/*` in that project, so internal aliased imports used by `server/domain/**` and `shared/types/**` don't resolve there. |

ESLint does not catch any of this: it lints one file at a time with no concept of "which TS project checks this file", so an import that's valid under `tsconfig.server.json` looks fine to ESLint even though it breaks under `tsconfig.node.json`. This is also why `yarn test` doesn't catch it — Vitest resolves paths via `vite-tsconfig-paths`/Vite's own resolver at runtime, not via `tsc`, so a broken *type-only* import can still execute fine while `tsc` rejects it.

## Current Usage Contexts

### 1. Source files relying on Nuxt's global type auto-imports
- `shared/types/rental.ts:1-47` — uses `EntityId`, `Enums`, `UserId`, `GearItemId`, `TopoId`, `ContactInfo` with zero imports.
- `shared/types/topos.ts:2` — writes `globalThis.TopoId` explicitly, an even more direct dependency on the global augmentation existing.
- `server/domain/inventory/ItemEvent.ts:6,10` — uses `RentalId` with no import.
- `app/model/Rental.ts:5,14,33,66,71,80,...` — uses `RentalId`, `RentalStatus`, `RentalItemId`, `GearItemId`, `TopoId`, `ContactInfo`, `UserId` with no imports, throughout a 305-line file.
- Contrast: `shared/types/gear.ts:1-4` already imports explicitly (`EntityId`, `RentalId`, `Date` from relative/aliased paths) — the codebase is inconsistent about this, not uniformly relying on globals.

### 2. Source files using internal path aliases across the server/shared boundary
- `server/domain/inventory/InventoryItem.ts:1` — `import type { ItemEvent } from '#server/domain/inventory/ItemEvent'` (works in `tsconfig.server.json`, which defines `#server/*`).
- `shared/types/gear.ts:1` — `import type { ItemEvent } from '~~/server/domain/inventory/ItemEvent'` with an explicit `// TODO: invalid dependency?` comment — `shared/` reaching into `server/domain/` is a boundary violation the original author already flagged.

### 3. Test files importing production source with a root-relative `~/`
- `test/unit/app/model/Rental.spec.ts:2-5` — `~/app/model/Rental`, `~/shared/types/gear`, `~/shared/types/rental`, `~/shared/utils/utils`.
- `test/testUtils/testDao.ts:2,4,5` — `~/shared/types/database.types`, `~/server/domain/inventory/InventoryItem`, `~/server/domain/inventory/ItemEvent`.
- `test/testUtils/MailpitService.ts:2-3`, `test/testUtils/TestUserService.ts:2,5`, `test/e2e/pages/rentals-overview.page.ts:2`, `test/e2e/pages/topos/details.page.ts:2`, `test/e2e/rentals.spec.ts:12` — same pattern, ~15+ call sites total.
- This `~` means "repo root" here, which directly contradicts the project convention (`ai-context/project-structure.md`, `nuxt.config.ts:104-105`) where `~` means `app/` and `~~` means root. The `nodeTsConfig.paths` override (`nuxt.config.ts:104-107`) was added specifically to make this second, contradictory meaning of `~` resolve for tests — it doesn't fix the transitive alias/global problems, it only patches the entry-point import.

### 4. Test-only aliasing convention
- `#test/*` → `test/*` and `test/testUtils/*`, defined only in `nodeTsConfig.paths` and used throughout `test/e2e/**` and `test/testUtils/**` (e.g. `test/e2e/rentals.spec.ts:8,10,11,14`). This alias works fine and isn't part of the problem — it's scoped correctly to test-only files.

## The Core Tension

There are two independent axes being conflated, and any fix has to address both:

| | Rely on Nuxt-generated globals for types | Import types explicitly everywhere |
|---|---|---|
| Verbosity | Zero import lines for `RentalId` etc. | One import line per type used |
| Portable across TS projects (app/server/shared/node/test) | No — only works where `.nuxt/*.d.ts` references the generated global block | Yes — works anywhere, including editors/tools with no Nuxt context |
| Consistent with existing code | No — `gear.ts` already imports explicitly; `rental.ts`/`ItemEvent.ts`/`Rental.ts` don't | Matches roughly half the codebase already |
| Depends on Nuxt internals (`.nuxt/nuxt.*.d.ts` reference graph) | Yes, entirely | No |

| | Tests share `tsconfig.node.json` with build config | Tests get their own TS project |
| --- | --- | --- |
| Number of `tsc` invocations needed for full coverage | 4 (current) | 5 |
| Risk of build-config-only assumptions (e.g. Node-only globals) leaking into app code checks | Low today, but only because it's currently broken silently | N/A — isolated project |
| Conceptual honesty (`node` project = "things Nuxt itself needs to build", not "anything importing app code") | No — test files aren't config, they got added because they had to live somewhere | Yes |
| Migration cost | None | Rewrite `~/` test imports, add a project + reference, extend `typecheck` script |

Both axes are genuinely orthogonal: you could fix the alias/global problem for the node project without ever touching the type-import style in source files, or vice versa. But doing only one leaves the other class of error unfixed (e.g. fixing aliases alone still leaves every `Cannot find name 'RentalId'` error, and fixing type imports alone still leaves `#server/*` unresolved for `ItemEvent.ts` inside the node project).

## Options

### Option A — Patch `tsconfig.node.json` in place (minimal, no code changes to source)

Fix `nodeTsConfig` in `nuxt.config.ts` to mirror the real aliases and pull in the generated globals, without introducing a separate test project — i.e. do what Option D does, but by hand-patching `nodeTsConfig`'s `paths`/`include` instead of extending `tsconfig.shared.json` via a new file.

**Pros**
- Smallest diff; no new tsconfig file, no `typecheck` script change.
- One command (`nuxt typecheck`) still covers everything.

**Cons**
- Every alias and global reference has to be kept in sync by hand inside `nuxt.config.ts` — the exact drift that caused this issue (`nodeTsConfig.paths` was written once, incompletely, and never revisited as `#server`/`#shared`/`~~` aliases were introduced elsewhere). Option D avoids this by inheriting rather than duplicating.
- `nodeTsConfig` conceptually stays "config files + arbitrary app/server/shared source", a wider blast radius than a project meant to check `nuxt.config.ts` and friends.
- Does not on its own address the `shared/types/gear.ts` → `server/domain` boundary violation (same as Option D, this is an independent follow-up either way).

~~### Option B — Explicit type imports + dedicated test TS project (structural fix)~~

**Discarded.** This option required adding explicit `import type { ... }` statements to `shared/types/rental.ts`, `shared/types/topos.ts`, `server/domain/inventory/ItemEvent.ts` and `app/model/Rental.ts` instead of relying on Nuxt's global type auto-imports. Nuxt's auto-import feature (including type auto-imports from `shared/types`) is something the project wants to keep using, so any option that requires writing manual imports to work around it is off the table. The valid part of this option — giving tests their own TS project — is kept and reworked into Option D below, without the explicit-import requirement.

~~### Option C — Explicit type imports only, keep tests inside `nodeTsConfig`~~

**Discarded** for the same reason as Option B: it also required explicit `import type` statements in source files to avoid relying on Nuxt's auto-imported globals.

### Option D — Dedicated `tsconfig.test.json` extending `tsconfig.shared.json` (recommended)

Give tests their own TS project, but instead of duplicating aliases/strictness by hand, have it **extend** the generated shared project so it inherits the same `paths` (`~`, `~~`, `#shared/*`, `#server/*` are already all correctly defined in `.nuxt/tsconfig.shared.json`) and the same reference to the file containing Nuxt's global type declarations (`shared-imports.d.ts`). No source file needs to change — auto-imported types keep working exactly as they do today, in every project.

1. Move `test/**` out of `nodeTsConfig` (leave `nodeTsConfig` covering only `nuxt.config.ts` / `vitest.config.ts` / `playwright.config.ts` / `content.config.ts` — genuine build-time config, nothing else).
2. Add a new, hand-written `tsconfig.test.json` at the repo root:
   ```jsonc
   {
     "extends": "./.nuxt/tsconfig.shared.json",
     "compilerOptions": {
       "paths": {
         "#test/*": ["./test/*", "./test/testUtils/*"]
       }
     },
     "include": [
       "./test/unit/**/*",
       "./test/integration/**/*",
       "./test/e2e/**/*",
       "./test/testUtils/**/*"
     ]
   }
   ```
   Reference it from the root `tsconfig.json`, and extend the `typecheck` script: `"typecheck": "nuxt typecheck && vue-tsc --noEmit -p tsconfig.test.json"`.
3. Rewrite the ~15 test imports from `~/shared/...`/`~/app/...`/`~/server/...` (which relied on `nodeTsConfig`'s special-cased `~/*` → repo root remap) to the aliases the rest of the codebase already uses: `~/model/...` (since `~` now correctly means `app/`, inherited from the shared project), `#shared/...`, `#server/...`.

Separately, and independent of this tsconfig fix: move `ItemEvent` from `server/domain/inventory/` into `shared/domain/` (mirroring the existing `shared/domain/rental` folder). This isn't required to make typecheck pass under this option — `#server/*` is a valid alias in the shared project already — but it resolves the `shared → server` dependency inversion that `shared/types/gear.ts:1` already flags with `// TODO: invalid dependency?`. Worth doing at the same time since it's low-cost and directly related to the files being touched, but it's a separate architectural decision.

**Pros**
- No source file changes, and no impact on Nuxt's auto-import feature — the exact requirement.
- Fixes both failure classes: correct aliases (inherited from `tsconfig.shared.json`) and correct global-type visibility (inherited via the same `.d.ts` reference chain the shared project already uses).
- `tsconfig.test.json` stays in sync with the shared project automatically — if Nuxt changes how it structures the shared project's aliases or global declarations in a future version, `tsconfig.test.json` picks up the change for free instead of drifting out of sync.
- `nodeTsConfig` goes back to being what it says on the tin: build-time config only.

**Cons**
- Still depends on Nuxt's generated `.nuxt/tsconfig.shared.json` and its reference graph existing in its current shape — this is an accepted, unavoidable dependency once the auto-import feature itself is required to keep working (per the note on Option B/C above: any solution that preserves Nuxt aliases/auto-imports depends on Nuxt's generated files to some extent; this option makes that the *only* remaining dependency, rather than adding manual-import maintenance on top of it).
- Two `tsc` invocations needed for full coverage instead of one; `typecheck` script (and CI, if it shells out to `nuxt typecheck` directly) needs updating.
- ~15 test files still need their `~/...` imports rewritten to match the corrected alias meaning.

## Recommendation

Option D. It fixes both failure classes (missing aliases, missing global type declarations) purely through tsconfig composition — extending the shared project's generated config rather than hand-maintaining a parallel copy of its aliases inside `nuxt.config.ts`. This directly avoids the failure mode that caused the original bug: `nodeTsConfig.paths` being written once and silently drifting out of sync as new aliases (`#server`, `#shared`, `~~`) were introduced elsewhere in the project. It requires no changes to any source file and has zero impact on Nuxt's type auto-import feature, per the explicit requirement to keep using it. Option A is a viable, smaller fallback if a second `tsc` invocation in the `typecheck` script is undesirable, but it reintroduces the same manual-sync risk that needs to be watched for over time.

## Decisions

- **Nuxt's type auto-import feature must keep working as-is.** No source file should need explicit `import type` statements purely to work around a TS-project boundary. This ruled out Options B and C outright and shaped Option D to solve the problem entirely through tsconfig composition instead.
- **`tsconfig.test.json` extends `.nuxt/tsconfig.shared.json`** rather than duplicating its `paths`/compiler options by hand.
- **`test/nuxt/**` is left untouched** — it's already correctly isolated in the app project via Nuxt's own test-utils wiring; the new `tsconfig.test.json` only needs to cover `test/unit`, `test/integration`, `test/e2e`, `test/testUtils`.
- **The 2 genuine bugs in the app project** (itemSelection generic emit mismatch in `app/components/board/rental/form/itemSelection/index.vue:108`, `onclick`/`onClick` typo in `app/components/profile/overview/membership/BuyMembership/Modal.vue:54`) are **out of scope** for this effort.
- **Enabling `typescript.typeCheck: true`** in `nuxt.config.ts:89` is **out of scope** for this effort.
